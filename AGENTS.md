# Contributor and agent rules

This file governs every agent (implementer or reviewer) working in this
repository. It is the operational counterpart to the design spec at
`docs/superpowers/specs/2026-09-25-xilinx-primitive-test-suite-design.md`
("the spec"). Where they conflict, the spec wins — file a docs PR to fix
this file rather than silently deviating from either.

## 1. Read first

Before touching any code:

- the **spec**, in full, and at minimum the sections cited from the task
  brief you were given;
- the **current plan** for the step you are executing, under
  `docs/superpowers/plans/`;
- this file, in full.

If a task brief and the current spec disagree (the spec is revised in
place; branches are cut from a point in time), the **current spec on
`main`** is authoritative. Say so in your log entry and proceed from it.

## 2. One branch per work unit, in its own worktree

Every unit of work — one work unit's primitives, one infra topic, one L3
integration design, one docs topic — gets its own branch, and every branch
gets its own git worktree so agents never collide on a shared working
directory:

```bash
git worktree add ../xilinx-unittests-worktrees/<branch-with-dashes> -b <branch>
```

For example, work unit `flops`:

```bash
git worktree add ../xilinx-unittests-worktrees/unit-7series-flops -b unit/7series/flops
```

Branch types (spec §13.2):

| Branch | Scope |
|---|---|
| `unit/7series/<unit>` | one work unit (`docs/work-units.yaml`) |
| `infra/<topic>` | shared code under infra-owned paths |
| `integ/<name>` | one L3 design, its own `tests/7series/integration/<name>/` |
| `docs/<topic>` | specs and plans (`docs/superpowers/**` only) |

Branches and PRs:

- One PR per branch, always. Never push work for a later PR onto a branch
  whose PR is open.
- A stacked branch is created from its parent branch, and its PR's base is
  the parent (`gh pr create --base <parent>`) until the parent merges.
- After a parent merges, only the orchestrator rebases the child onto
  `main`, re-runs its tests, pushes with `git push --force-with-lease`
  (only on its own feature branches; never on `main`, never over someone
  else's branch), and retargets the PR with `gh pr edit <N> --base main`.
  This is the only sanctioned force-push; the rule against force-pushing
  reviewed history still applies to everyone else.
- Reviewers run sequentially under the two-agent limit.

## 3. Only touch owned paths

`docs/work-units.yaml` maps each work unit to its primitives;
`xut.workunits.owned_paths` derives the glob patterns it owns. What a
branch may touch is determined by its **type** (spec §13.2); this is what
`xut lint --branch` (Task 8) enforces:

| Branch | Owns |
|---|---|
| `unit/<family>/<unit>` | `owned_paths(unit)` — tests, `<PRIM>.overrides.yaml`, its models (including `_common/<unit>.py`), status files, findings — plus its own log files |
| `integ/<name>` | `tests/7series/integration/<name>/**`, plus its own log files |
| `docs/<topic>` | `docs/superpowers/**` (specs and plans only), plus its own log files |
| `infra/<topic>` | anything **except** paths owned by a work unit — this includes the generated `catalog/<family>/<PRIM>.yaml` files, `docs/work-units.yaml`, `docs/review/**` and `docs/templates/**`. One exception: infra may **add** a new `status/<family>/<PRIM>.yaml` stub, but never modify or delete an existing status file (that is the owning unit's) |

Shared test code for a unit (generator helpers, sv bodies, the cocotb session,
metadata generators) lives in `tests/<family>/<group>/_shared/<unit>/`, which
`owned_paths(unit)` includes; runners put it on the test's search path
(`TestCase.shared_dirs`).

Every branch, of every type, may also add its own progress-log entries:
`log/<YYYY-MM-DDTHHMM>-<own-branch-slug>-<slug>.md`, where `<own-branch-slug>`
is `xut.workunits.branch_slug(branch)` — the branch name with every `/`
replaced by `-` (rule 6). A branch never writes another branch's log
entries.

Before every push:

```bash
uv run xut lint --branch
```

This fails if the branch has touched a path outside what its type owns per
the table above.

## 4. Small commits

Commit after every meaningful change — including log and status updates,
not just code. Subjects are prefixed `<unit|area>: ` (e.g. `flops: add FDRE
L1 reset-over-CE vector test`, `infra: add work-unit loader`).

Install the commit-msg hook so a malformed subject is rejected locally,
before it reaches review:

```bash
git config core.hooksPath tools/hooks
```

## 5. Never commit generated files

`status/PROGRESS.md`, `status/TODO.md`, `status/LOG.md` and
`status/PORTABILITY.md` are generated by `xut status` and committed **only**
by the orchestrator on `main`, in a dedicated `status: regenerate` commit
(spec §11). Never commit them from a work-unit, infra, integ or docs
branch.

Never commit AMD PDFs or AMD prose. The catalog stores facts (names,
widths, values, page numbers) and short paraphrases only (global
constraints; spec §3).

## 6. Progress log

Add one log entry per session:

```
log/<YYYY-MM-DDTHHMM>-<branch-slug>-<slug>.md
```

`<branch-slug>` is the branch name with `/` replaced by `-` (branch
`unit/7series/flops` → `unit-7series-flops`). Pick a short, distinctive
`<slug>` so filenames stay unique. State:

- what changed;
- test results (what ran, what passed/failed/skipped and why);
- next steps.

## 7. Status

Update `status/7series/<PRIM>.yaml` whenever a result changes: a new
level × runner × flow result, a new finding, a coverage bin flipping
covered/uncovered. Record it with `xut status record`, never by hand. That
command writes the tree hash and the tool versions per model source (spec §11).

The tree hash covers the primitive's unit-owned inputs:
- `tests/<family>/<group>/<PRIM>/` and `tests/<family>/<group>/_shared/<unit>/`;
- the golden model (`<prim>.py` and `_common/<unit>.py`);
- `<PRIM>.overrides.yaml`.

Record in this order:
1. Commit those inputs.
2. `xut run` against each model source: it stamps `tree_hash`, `head` and
   `dirty` into every `result.json`.
3. `xut status record`.

`xut status record` refuses uncommitted inputs, and any result that is stale
(another tree hash) or dirty. After changing an input, commit and re-run;
there is no override. Each model source keeps its own tree hash, tools and
results (`results_by_model_source`).

`xut status init --refresh-bins` updates the bins of never-recorded stubs to
the current catalog. The orchestrator runs it on `main` only.

## 8. Clean-room golden models

Write golden models (`models/xut_models/7series/<prim>.py` and the shared
`_common/<unit>.py`) **from UG953 only**. Never open UNISIM source while
writing or editing a model — that is what the model is being cross-checked
against, and reading it defeats the cross-check.

Tag every modelled behaviour with its provenance:

- `doc:<page>` — taken directly from a numbered UG953 page;
- `inferred:<reason>` — the documentation is silent and the behaviour was
  inferred (state the reasoning in `<reason>`).

A don't-care (`-`) output bit is allowed only where UG953 *declares* the
value undefined, so its provenance is always `doc:<page>` (spec §5.3). Where
UG953 is silent, give a definite `inferred:` value: a disagreement then
becomes a `doc-gap` finding in crosscheck, never a mask. The model API
(`Out`) refuses a `-` bit with an `inferred:` tag.

## 9. Never weaken a test to hide a divergence

If a test disagrees with an oracle, classify and record it — don't touch
the test to make the disagreement go away. Write
`findings/<PRIM>-<slug>.md`, using the classes in spec §8
(`doc-vs-model`, `doc-gap`, `sim-divergence`, `x-dependence`,
`transform-bug`, `flow-mismatch`, `silicon-mismatch`, `nondeterminism`,
`harness-error`). Link it from the primitive's README, and optionally from
an `expected_divergence` entry in `test.yaml` (the `expected_divergence`
field arrives in step 2; `test.schema.json` does not accept it yet).

**An expected divergence never masks** (spec §8, rev 3.1). Listing a
disagreement in `expected_divergence` does not suppress it:

- the expected bits stay defined — never turn one into a don't-care;
- the disagreement is still computed and reported, classified
  `known-divergence` with the finding id (and its original class);
- it stays visible in PROGRESS.md and TODO.md for as long as the finding
  is open, and every entry must reference an existing, **open**
  `findings/*.md`;
- `xut crosscheck` fails on any disagreement that no `expected_divergence`
  entry lists.

## 10. Shell rules

- Never use `2>/dev/null`. It hides the errors you need to diagnose a
  failure.
- Redirect long-running or verbose command output to a log file, then
  inspect the log file.
- Vivado is only ever sourced in a subshell, never in the interactive
  shell:

  ```bash
  bash -c 'source /opt/xilinx/Vivado/2025.2/settings64.sh && ...'
  ```

## 11. SPDX header

Every source file (`.py .v .sv .yaml .sh .tcl .toml`, workflow files)
starts with:

```
# SPDX-License-Identifier: Apache-2.0
```

(or the file format's equivalent comment syntax). Markdown files are
exempt. `xut lint` checks for it.

## 12. Review

Every PR — work unit, infra, integ or docs — gets two fresh reviewer
agents (spec §13.4):

- **(a) code quality**, using `docs/review/code-quality.md`;
- **(b) correctness**, using `docs/review/correctness.md`.

Reviewers post findings with `gh pr review <N> --comment --body-file
<file>`, each line marked **[must-fix]** or **[nit]**. Address every
must-fix in new commits (never by amending or force-pushing over
reviewed history) and ask for re-review. The one exception: after
rebasing a dependent branch (spec §13.3), **only the orchestrator** may
`git push --force-with-lease` its own feature branches (controller
Ruling 17); implementers and reviewers never force-push. The merge gate is: `xut lint`
passes, CI is green, both reviewers approve with no open must-fix.

**Concurrency (spec §13.5).** At most **two sub-agents in total, reviewers
included**, run at any time — normally one implementer plus one reviewer.
The orchestrator itself does not count against this limit.

## 13. Infra dependencies

If a unit branch needs a change to an infra-owned path, you may not make
it yourself (rule 3). Instead:

- record a TODO in your log entry and continue with what you can do
  without it, **or**
- stack your branch on the open `infra/*` branch that will provide it.

Never edit infra paths from a unit, integ or docs branch. Merge order is
always infra first; the orchestrator rebases dependent branches and
re-runs their tests afterwards.

## Catalog notes

- The catalog (`catalog/7series/<PRIM>.yaml`) is generated from UG953 and
  UNISIM and is infra-owned; do not hand-edit it. Its `allowed` values for
  an attribute are **advisory**, not verified against silicon or even
  fully cross-checked against the documentation table layout — see
  `catalog/EXTRACTION_REPORT.md` for the list of names/values the
  extractor could not resolve. Correct them for your primitives in
  `<PRIM>.overrides.yaml`, which your work unit owns.
- A port's class (spec §5.1) can be configuration-dependent. For example,
  IDDR/ODDR's `S`/`R` port is `async` under `SRTYPE=ASYNC` but behaves
  differently under `SRTYPE=SYNC`; declare the per-configuration class in
  the primitive's overrides rather than picking one class for every test.
- Verilator never runs stock UNISIM directly. It only ever sees a model
  after `xut verilatorize` (spec §6.2) has rewritten its
  `assign`/`deassign` forced-register constructs into the shadow-register
  form; the transformed copy lives under `build/verilatorized/` and is
  never committed. Any test that declares a `verilator` result implicitly
  depends on that transform having an equivalence stimulus (spec §6.2).
  From step 2, `xut lint` fails a transformed model with none (not
  enforced yet).
- `transform-bug` (spec §8) is a real finding class: it means Icarus
  disagrees between the original and the `verilatorize`-transformed
  model, i.e. the transform itself is wrong, not the primitive under
  test. Treat it as a blocker on the Verilator result for that model, and
  file it like any other finding.
